# Mesh backend

Go 1.25+, PostgreSQL 17. Один backend с режимами `api` и `worker`; логические владельцы — demo, inventory, routing/orders, exceptions и finance. HTTP-контракты читаются из `../docs/openapi`, пути `/api/v1` и `/internal/v1`. Единственная внешняя зависимость исполнения — PostgreSQL; аутентификация использует подписанные JWT.

## Локальный запуск

Команды из каталога `backend/`. PostgreSQL ниже предназначен только для синтетической демонстрации. Если порт 55432 уже занят тестовым экземпляром `rwb-mesh-test`, используйте его или остановите его перед Compose.

```sh
docker compose up -d --wait
export MESH_DATABASE_URL='postgres://mesh_test:mesh_test@127.0.0.1:55432/mesh_test?sslmode=disable'
export MESH_TEST_DATABASE_URL="$MESH_DATABASE_URL"
export MESH_USER_JWT_SECRET='local-demo-user-secret-at-least-32-characters'
export MESH_SERVICE_JWT_SECRET='local-demo-service-secret-different-32-characters'
export MESH_JWT_ISSUER='mesh-local'
go build -o /tmp/mesh ./cmd/mesh
/tmp/mesh migrate
/tmp/mesh import --dataset testdata/demo
/tmp/mesh api --addr 127.0.0.1:8081 --contracts ../docs/openapi
```

В другом терминале с тем же `MESH_DATABASE_URL`:

```sh
/tmp/mesh worker
```

В третьем терминале с тем же `MESH_USER_JWT_SECRET` и `MESH_JWT_ISSUER`:

```sh
export MESH_TOKEN="$(/tmp/mesh token --subject demo-user --roles dispatcher,demo_admin)"
python3 scripts/demo_order.py
```

Сценарий создаёт чистый прогон, рассчитывает котировку, оформляет заказ и проходит сборку, передачу, прибытие и выдачу. Проверяет остаток 4 из 5 единиц и наличие проводок. `/healthz` проверяет БД. API доступен по `http://127.0.0.1:8081/api/v1`.

Frontend использует `VITE_API_BASE_URL=http://127.0.0.1:8081/api/v1` и существующий `ApiContext.getAccessToken` для передачи токена. Для отдельного origin задайте `MESH_CORS_ORIGIN` при запуске API, например `http://localhost:5173`. Секреты из примера предназначены для локальной демонстрации. Пользовательский JWT: HS256, `iss=MESH_JWT_ISSUER`, `aud=mesh-user`, `sub`, `exp`, `roles`, `pvzIds`, `sellerIds`. Сервисный JWT подписывается отдельным секретом, `aud=mesh-internal`, `sub` — имя сервиса из `x-callers`. Gateway обязан передать подписанный пользовательский JWT в `X-User-Context`; область не берётся из неподписанных заголовков. Внешний провайдер JWT и выдача настоящих учётных записей находятся за пределами backend.

## Данные и воспроизводимость

`testdata/demo` — самостоятельный синтетический входной снимок с явными партиями, ёмкостями, остановками, временем и тарифами. Он не восстановлен из `expected.json` существующих наборов. Первоначальные наборы в `../datasets` не содержат всех необходимых входных снимков; импорт отклоняет их с конкретной причиной. Ожидания и будущие заявки не превращаются в исходный запас.

```sh
/tmp/mesh import --dataset testdata/demo
/tmp/mesh import --all --dataset ../datasets
```

Повтор той же версии безопасен, контрольные суммы проверяются повторно. Ошибочная версия не публикуется. `--all` обрабатывает независимые наборы и возвращает ошибки неполных. JSON-снимки и CSV читаются по манифесту с проверками ключей и ссылок. Parquet в готовых файлах репозитория отсутствует; неподдерживаемый формат явно отклоняется.

Версия набора неизменяема. Прогон хранит ссылку на неё, параметры и часы; изменения записываются поверх по `run_id`. Чистый прогон не копирует каталог и заказы. Запросы остатков и кандидатов маршрута используют индекс JSONB и индекс ключа. Для транзакционных инвариантов команды одного прогона сериализуются advisory lock; разные прогоны независимы. Это сознательный компромисс прототипа: безопасная атомарность вместо параллельной записи внутри одного прогона.

Все команды с `202` сохраняются вместе с `Operation`. Worker берёт устойчивое задание через `FOR UPDATE SKIP LOCKED`; изменение состояния и завершение задания фиксируются одной транзакцией. При ошибке БД транзакция откатывается и задание доступно повторно. Бизнес-ошибка записывается в `Operation.error`. Повтор по ключу возвращает исходный результат, включая ID операции, даже после смены версии ресурса.

## Проверки

Тесты используют только отдельный локальный PostgreSQL `mesh_test`, синтетические снимки и подписанные тестовые токены. `TestStore` отвергает обычные адреса БД; при отсутствии тестовой БД тесты завершаются ошибкой. Реальные хранилища и внешние сервисы не используются. PostgreSQL выбран для E2E по прямому требованию задания.

```sh
go test -race ./... -count=1
go vet ./...
go build ./cmd/mesh
MESH_RUN_SCALE=1 go test ./internal/core -run '^TestImportLargeSlice$' -count=1 -v
```

HTTP E2E проверяют доставку и фактические остатки/проводки, локальную выдачу, смешанную корзину, конкуренцию за последнюю единицу, ошибку вместимости, пересчёт маршрута, частичный повреждённый возврат, пороги хранения и вывоз, изоляцию прогонов, идемпотентность, авторизацию, пагинацию и ответы OpenAPI. Отдельный тест прерывает фиксацию результата воркера после изменения заказа и подтверждает полный откат и однократную выдачу после перезапуска.
