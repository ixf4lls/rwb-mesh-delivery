# Mesh Delivery · Промпты для генерации тестовых данных

Скопируй промпт 0 в Codex, затем отправь промпт нужного набора. Для генерации всех наборов в одной сессии отправь блоки 1–7 после блока 0. Каждый блок добавляет сценарий в один и тот же генератор. Число ПВЗ и ставки заданы для эксперимента. Перед использованием открой в корне репозитория `docs/openapi/README.md`, `docs/openapi/frontend.yaml` и `docs/openapi/internal.yaml` (версия контрактов 0.1.0). Результат работы по промптам — готовые файлы тестовых данных, каталог для выбора в демо и проверки этих файлов.

| 1 | Сквозные операции с проверяемым результатом | 8 случаев, 7 заказов |
| 2 | Плотный спрос и выдача с полки | 1 600 заказов за 28 дней |
| 3 | Редкий спрос и дорогие остановки | 400 заказов за 28 дней |
| 4 | Дефицит места и задержка курьера | Те же 1 600 заказов, что в наборе 2 |

## Промпт 0. Общий генератор и правила модели

```text
Подготовь для rwb-mesh-delivery воспроизводимые файлы тестовых данных. Сверь их с docs/openapi/frontend.yaml (публичный API /api/v1), docs/openapi/internal.yaml (межсервисный API /internal/v1) и docs/openapi/README.md. Для генерации и проверки файлов можно использовать скрипт с командами generate, validate, estimate, параметрами сценария, seed (42 по умолчанию) и каталога вывода. В эту задачу входят сами наборы, команды их воспроизведения и контрольные ожидания. Реализация приложения, загрузка в PostgreSQL и вызовы работающих сервисов за рамками задания.

Каталог для быстрого переключения. Подготовь datasets/catalog.json в форме DatasetPage с массивом items. Для каждого готового набора добавь Dataset с полями id, name, summary, status, seed, initialClock, pointCount, orderCount. Допустимые статусы — ready и unavailable. Для каждого набора создай datasets/<id>/ с manifest.json, исходными таблицами и expected.json для контрольных примеров. В manifest укажи версию схемы, период, контрольные суммы и число записей, различай подготовленные заказы и будущие заявки на заказ. Внутри manifest задай стартовый город, ПВЗ, время и интересующую запись для показа. Эти подсказки принадлежат файлам демонстрации. В объект Dataset, возвращаемый API, включай только его поля. Случаи внутри demo могут ссылаться на один и тот же подготовленный набор.

Проверка выбора в приложении. GET /demo/datasets под ролью demo_admin показывает каталог. GET /demo/context возвращает DemoRun текущего контекста. Роль demo_admin создаёт чистый прогон через POST /demo/runs с datasetId, expectedContextVersion и заголовком Idempotency-Key. При активном прогоне бери expectedContextVersion из его contextVersion. Успешный ответ — 201 DemoRun. Для нового чистого прогона нужен новый ключ; сетевой повтор прежней команды использует прежний ключ. Для доменных запросов в деморежиме заголовок X-Demo-Run-Id содержит id активного прогона. При смене набора перечитай контекст. В начальных данных предоставь профили для /me с допустимыми roles, pvzIds, sellerIds, чтобы оператор видел свои точки, а продавец — собственные SKU. Диспетчер может демонстрировать смешанную корзину нескольких продавцов.

Что генерировать:
1. Сеть. City содержит id, name, timeZone. У Node обязательны id, cityId, name, kind, active, mode; kind принимает pickup_only, storage_pvz, sorting_center, hub. PickupPoint вкладывает node и добавляет acceptsOrders, acceptsReturns, openingHours (weekdays 1–7, opens, closes). Подготовь узлы и связи также для возврата и резервного пути. Размеры в слотах представь схемой Capacity: totalSlots, storageQuotaSlots, storageUsedSlots, ordinaryUsedSlots, pickupUsedSlots, inboundReservedSlots, availableStorageSlots, availablePickupSlots на pointId и asOf. Координаты, районы, смены, очередь, история спроса и статистика карты — локальные данные симуляции; свяжи их по ID с контрактными сущностями. Время в API — RFC 3339, суточные объёмы и расписания проверяй по timeZone города.
2. Продавцы, товары, партии. Для ProductCreate используй sellerId, sellerSku, name, weightGrams, slotsPerUnit, salePriceMinor, unitCostMinor и при необходимости category. Product.id обозначает товар в ссылках productId; sellerSku — артикул продавца. Для приёмки в ПВЗ используй BatchReceipt с productId, storagePointId, quantity и при необходимости externalLotRef. ID партии, продавца и receivedAt определяет сервис. Для ранее принятой партии подготовь снимок Batch с receivedQuantity, availableQuantity, reservedQuantity, packedQuantity, quarantinedQuantity, usedSlots, тарифом и receivedAt. Количество на полке равно сумме четырёх текущих состояний, включая карантин. Складской запас хаба, предзаказный завоз, источники пополнения и товар в пути описывай в исходном состоянии. POST /batches моделирует приёмку уже прибывшей в ПВЗ партии.
3. Спрос, котировки, заказы. План спроса хранит устойчивые ключи заявки и строк, время, выбранный ПВЗ и состав. При воспроизведении POST /quotes принимает QuoteRequest с pickupPointId и items[{productId, quantity}], каждый productId встречается один раз. Цены, партии, рейсы, тариф и варианты рассчитывает сервер. POST /orders принимает OrderCreate с quoteId и, если нужен конкретный выполнимый вариант, optionId. Если все варианты исключены, рекомендованный отсутствует. Сохрани привязку ключей теста к выданным ID. В снимке Order проверь все обязательные поля, включая version, routeRevision, quoteId, promisedReadyAt, estimatedReadyAt, settlementStatus, lines и shipments. OrderLine.id — значение orderItemId в возврате и резерве. Если CSV или Parquet использует snake_case, приложи явное соответствие полей контракту. ID в API удовлетворяют ^[A-Za-z0-9_-]+$ и ограничены 128 символами.
4. Движение. До заказа обычный запас лежит на хабе; после заказа он едет через СЦ и последнюю милю. Mesh-партия из 5, 10 или 20 единиц заранее прибывает через СЦ в ПВЗ хранения; возможна выдача на месте, соседний ПВЗ ежедневным рейсом и исполнение с хаба при нехватке. В СЦ товар проходит транзитом. Для одной корзины Quote.options включает mesh_only и hub_only, hybrid возможен при разделении источников. Отличай policy от mode (local_shelf, city_mesh, hub, mixed). Невыполнимый вариант содержит feasible=false и reasons. Пути описывают shipments и упорядоченные segments, идентификатор рейса — Segment.tripId; внутреннее распределение количества по партии и отправлению — Allocation. В Segment используй distanceMeters, waitMinutes, scheduledStartAt, scheduledEndAt, estimatedCostMinor, costItems и поля рейса, где применимо. Для моделируемых хаба и магистрали задай mode=simulated. Запиши календарь, отсечки, фоновый груз, стоимость машины и разницу между плановым и дополнительным заездом.
5. Выдача. Резервируется вся корзина и нужная ёмкость. Команда packed для shipmentId переводит резерв в упаковку. Для перевозимого отправления передавай handed_over и arrived с shipmentId и segmentId по фактическим сегментам. Первая физическая передача уменьшает запас источника. На местной полке физическое выбытие происходит при выдаче. Все отправления должны быть готовы в выбранном ПВЗ до команды issued; issued относится ко всему заказу. В командах используй текущую expectedVersion, в снимках Order и OrderShipment — собственные перечисления status. Цена покупателя buyerFeeMinor, обещание promisedReadyAt, обновляемый прогноз estimatedReadyAt и затраты сети estimatedCostMinor принадлежат разным полям.
6. Возвраты, инциденты, часы. Тестовое намерение возврата относится к заявке; ReturnCreate возможен после issued. Укажи orderId, returnPointId, reason и lines[{orderItemId, quantity}], точка принимает возвраты. Предусмотри received_from_customer, транспортные handed_over и arrived по segmentId при перевозке, затем inspected с разбиением каждой строки на resellableQuantity и quarantinedQuantity. Для срыва рейса используй IncidentCreate, для нового маршрута — RerouteCommand. Сохрани expectedVersion для переходов соответствующего ресурса и expectedOrderVersion для запроса пересчёта. POST /demo/clock/advances принимает абсолютное будущее to и актуальный X-Demo-Run-Id. Запланированные внутренние переходы оформляй по SimulatedOrderAction и SimulatedExceptionAction из internal.yaml. Для первого обязательны id, dueAt, orderId, command; для второго — id, dueAt и ровно одна пара: returnId с returnCommand или caseId с transferCommand. Операторские действия оставь в сценарии ручного показа. Внутренний вызов от demo помечается X-Simulation-Action-Id. Новую ожидаемую версию бери после применения предыдущего этапа. Намерения оформить заказ или возврат, перегрузка точки и иные внешние воздействия описываются отдельными входами сценария. Перевод часов обрабатывает только поддержанные запланированные этапы и проверки хранения.
7. Экономика. Задай внутренний TariffVersion с currency=RUB, сроком действия, storageThresholdDays, maximumDeliveryMinutes и rates[{code, unit, amount}]. Денежные ставки — в целых копейках, процентные — в basis_point. Учитывай хранение за полные 24 часа с приёмки единицы по закреплённому тарифу, обработку, сортировку, магистраль, рейс, остановку, оплату ПВЗ, себестоимость и возврат. StorageCost различает accruedMinor и postedMinor. Для подтверждённых начислений используй LedgerEntry с sourceEventId и tariffVersionId, для сторно — также originalEntryId. При сверке аналитики используй проведённые записи за [from, to), раздельно для ПВЗ, продавца и маркетплейса. Сохраняй исходную цену покупателя. Внутренние переводы не создают дополнительной прибыли цепочки.

Подготовь файлы в UTF-8 CSV для небольших таблиц, JSON для настроек, примеров команд и ожиданий, Parquet для больших фактов с разбиением по городу и дню. Различай подготовленный снимок, намерение покупателя, тело запроса и проверяемый результат. Если прокручиваешь сценарий с начала, предстоящие выдачи и проводки описывай в ожиданиях. Если начинаешь с подготовленного снимка, согласуй статусы, остатки, резервы, тарифы, версии, журнал и модельное время. Идентичные входы используются в обоих прогонах: до предварительного размещения суммарный запас одинаков, после него оплачиваются завоз всей партии и хранение непроданного остатка.

Для сценариев 1–5 используй общую географию: город А с хабом и СЦ, город Б с СЦ и 6 ПВЗ (2 с хранением и выдачей, 4 только с выдачей), 1 межгородская линия, 2 городских маршрута с ежедневными рейсами. Общий каталог — 3 продавца и 12 SKU: по 2 SKU на каждую комбинацию высокого, среднего или низкого спроса и компактного или объёмного товара. Для экономических наборов 2–5 подготовь 56 дней истории, включая нулевой спрос: 56 × 6 × 12 = 4 032 строки. Задай 8 пар SKU × ПВЗ хранения, для которых можно проверить объём размещения 0, 5, 10 и 20 единиц; вариант 0 оставляет товар на хабе. Для наборов 1–6 по умолчанию одна позиция по одной единице в заказе. Специальные условия сценария имеют приоритет.

Для каждой JSON-записи, предназначенной для API, укажи контракт, имя схемы и направление (запрос или ответ). Проверь required, типы, enum, ограничения, oneOf и разрешённые поля, включая вложенные объекты. Для ручного примера дай шаг, роль, тело, требуемые заголовки, ожидаемые код и состояние. Команды с 202 возвращают Operation: ожидай терминальный результат по Location; при succeeded используй resourceId, при failed — error. Проверку итоговых денег делай после settlementStatus=posted. У команд с Idempotency-Key повтор тех же тела и ключа даёт тот же результат. Проверяй версии и ссылки внутри выбранного прогона; одноимённые записи в разных наборах не пересекаются. Проверь внешние ключи, уникальность ID, хронологию, суммы строк и баланс единиц товара. При наличии симуляции проверь, что запас и свободная ёмкость не уходят в минус, одна строка заказа не списывается дважды, в СЦ не начисляется длительное хранение, возврат возможен только после выдачи и в пределах выданного количества. Отрицательный пример приёмки проверь как HTTP 409 с application/problem+json. Зафиксируй, какие запросы предполагают роли pvz_operator, seller, dispatcher или demo_admin. POST /demo/runs и POST /demo/clock/advances требуют demo_admin, принятие решения по StorageCase и пересчёт маршрута выполняет dispatcher. Для экономических прогонов подготовь сверку по городу, ПВЗ и SKU: выдача с местной полки, доставка между ПВЗ и через хаб, загрузка рейсов, дополнительные остановки, слот-дни, остатки, затраты на выдачу, цена и срок для покупателя, результаты ПВЗ, продавца и маркетплейса.
```

## Промпт 1. Сквозная демонстрация

```text
Добавь один подготовленный набор demo с восемью независимыми случаями и семью заказами за полный сценарий. Дай случаям собственные ключи, партии и непересекающиеся остатки. Для отдельного показа создаётся чистый DemoRun этого же набора. Предусмотри выбор стартового примера в manifest и привязку условных ID к реальным ресурсам при воспроизведении команд. Для каждого дай исходное состояние, упорядоченные входные события, команду запуска и конкретные ожидаемые остатки, статусы и начисления.

1. Один городской заказ. В S1 принята партия из 5 единиц, покупатель выбрал ПВЗ P2, рейс ходит раз в день. После передачи одной единицы в S1 остаётся 4; в P2 выдана 1. Проверь packed → handed_over → arrived по отправлению и перевозимому сегменту, затем issued по заказу. Видны cutoffAt и время готовности.
2. Один межгородской заказ. Нужный SKU есть только на хабе города А. Проверь магистраль, оба СЦ, последнюю милю и начисления за каждый этап. В первой котировке mesh_only исключён из-за отсутствия локального запаса, hub_only выполним. Для сравнения подготовь отдельное исходное размещение партии в городе Б и вторую котировку той же корзины. Сравни estimatedCostMinor, buyerFeeMinor, etaMinutes и причины обоих вариантов.
3. Один заказ с двумя разными SKU по 1 единице. После выдачи покупатель возвращает одну позицию. Проверь, что обе строки выданы. Верни одну через POST /returns, после приёмки и inspected пополни доступный остаток на 1 и проверь сторно только этой строки. Вторая остаётся проданной. Используй разные источники для двух строк в контрольной корзине, если оба отправления допустимы. Тогда дополнительно проверь mode=mixed и готовность заказа только после прибытия последнего отправления.
4. Один заказ со срывом рейса после сборки. Укажи конкретный отменённый рейс, доступную альтернативу и обещанный срок. Создай инцидент trip_disrupted с orderId, shipmentId и failureTarget.tripId. Диспетчер запрашивает POST /incidents/{incidentId}/reroutes с expectedOrderVersion. В ожиданиях укажи новую RouteRevision от lastKnownNodeId, previousRevision, deltaCostMinor, deltaEtaMinutes и уведомление route_changed. Сохраняются исходные buyerFeeMinor и promisedReadyAt. Исключи повторный резерв товара. Для варианта без альтернативы ожидай статус инцидента blocked и уведомление reroute_blocked.
5. Ноль заказов, партия из 5 компактных единиц по 1 слоту. Стартовый возраст нулевой, тариф 2 ₽ за слот-сутки, порог 10 суток. После 10 полных суток начислено 100 ₽. Установи initialClock на момент приёмки и переведи часы на 10 полных суток вперёд. Ожидай billableSlotDays=50, accruedMinor=10000, открытый StorageCase и уведомление long_storage. Затем диспетчер выбирает transfer_to_hub с reason и expectedVersion. Проверь transfer_planned, освобождение слотов при фактической передаче и closed после прибытия на хаб. При повторе той же команды начисление не дублируется.
6. Один заказ с выдачей в самом S1. Покупатель выбрал точку хранения, товар есть на полке. Для выполнимого варианта ожидай mode=local_shelf, сегмент on_site. После packed отправление готово, до issued единица остаётся на полке. Проверь физическое выбытие при выдаче.
7. Два одновременных заказа на последнюю единицу в S1. Подготовь две котировки до резервирования. Воспроизводимый последовательный пример закрепляет последнюю единицу за первым подтверждённым заказом. При реальной конкуренции проверь ровно одного победителя без требования к его ID.
```
