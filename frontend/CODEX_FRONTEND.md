# RWB Mesh Delivery --- Frontend

## 1. Цель проекта

Разработать frontend MVP системы Mesh-доставки RWB. Backend разрабатывает другой участник команды. Единое веб-приложение включает кабинет ПВЗ, кабинет продавца и страницу «Модель доставки».

## 2. Стек технологий

-   React + TypeScript + Vite.
-   CSS Modules.
-   React Router.
-   Redux Toolkit + RTK Query.
-   REST API.

## 3. Обязательные действия перед началом разработки

1.  Изучи структуру репозитория, текущую ветку, состояние Git и существующий frontend.
2.  Изучи AGENTS.md и соблюдай его инструкции.
3.  Изучи актуальную документацию OpenAPI в `docs/openapi`.
4.  Изучи доступные контракты backend, модели данных и правила обработки ошибок.
5.  Сообщи мне, какие файлы документации изучены, какие endpoints доступны, какие операции MVP они покрывают и какие вопросы или недостающие контракты обнаружены.
6.  Предложи план первого этапа и дождись моего разрешения.

До моего подтверждения не создавай ветки, не изменяй файлы и не начинай реализацию. Не утверждай, что изучил документацию, если она недоступна.

## 4. REST API и OpenAPI

Документация: `docs/openapi` (относительно корня репозитория).

Ссылка: https://github.com/ixf4lls/rwb-mesh-delivery/tree/3202602de041efa588f0250102c10e8448014636/docs/openapi

-   Приоритет имеет актуальная локальная документация: ссылка ведёт на конкретный коммит.
-   Перед каждой фичей проверяй актуальность контрактов.
-   Соблюдай endpoints, HTTP-методы, параметры, структуры запросов и ответов, правила обработки ошибок.
-   Создавай TypeScript-типы на основе OpenAPI.
-   Используй RTK Query для запросов, кеширования и обновления данных после операций.
-   Используй Swagger для проверки API, если он доступен.
-   Не придумывай endpoints и не изменяй документацию или backend.
-   Если API отсутствует или расходится с документацией, сообщи мне. Временные заглушки используй только с согласования и явно обозначай их.
-   Финансовые расчёты, маршрутизация, резервирование и изменение остатков выполняются backend.

## 7. Этапы реализации

### Этап 1. Инициализация проекта

Ветка: `feature/init-frontend`

-   Создание React + TypeScript + Vite, если проект ещё не создан.
-   Структура проекта, маршрутизация, Redux и базовая настройка REST API согласно OpenAPI.

### Этап 2. Основной интерфейс

Ветка: `feature/app-layout`

-   Шапка, боковое меню, переключение ролей.
-   Общие кнопки, таблицы, поля ввода, модальные окна и дизайн-система.
-   Демонстрационное переключение ролей; 

### Этап 3. Кабинет сотрудника ПВЗ

Ветка: `feature/pvz-dashboard`

-   Очередь задач, приёмка товаров и партий, размещение на хранение.
-   Идентификатор, продавец, количество, характеристики, место и дата приёмки.
-   Остатки, вместимость, свободные места, загруженность ПВЗ, ближайший рейс при наличии данных.
-   Сборка и выдача заказов, подтверждение статусов без повторного списания товара.

### Этап 4. Кабинет продавца

Ветка: `feature/seller-dashboard`

-   Регистрация товаров и партий, выбор места хранения (ПВЗ или хаб).
-   Просмотр товаров, остатков на ПВЗ и хабах, резервов и заказов.
-   Тарифы и стоимость хранения, выручка, расходы и прибыль.

### Этап 5. Интерактивная модель доставки

Ветка: `feature/delivery-model`

Для визуализации логистической сети использовать
React Flow (`@xyflow/react`).

#### 5.1. Интерфейс

Создать отдельную страницу «Модель доставки».

- Слева — параметры моделирования, выбор города,
  товара, тестового заказа и ПВЗ.
- В центре — интерактивная логистическая сеть
  с узлами и направленными стрелками.
- Справа — сравнение классической доставки
  и Mesh-доставки.
- Снизу — экономическая аналитика и обоснование
  выбранного маршрута.

#### 5.2. Работа с заказами

- Создание демонстрационного заказа.
- Выбор товара и количества.
- Выбор ПВЗ получения.
- Резервирование товара через REST API.
- Получение доступных вариантов доставки.
- Отображение выбранного маршрута.
- Сравнение Mesh и классической схемы
  для городских и межгородских заказов.

#### 5.3. Визуализация маршрутов

Узлы графа:

- Продавец.
- ПВЗ хранения.
- ПВЗ выдачи.
- Промежуточные ПВЗ.
- Хабы.
- Покупатель.

На каждом ребре графа отображать:

- Стоимость перевозки.
- Расстояние.
- Время доставки.
- Направление движения товара.

При выборе ПВЗ отображать:

- Название и адрес.
- Рейтинг.
- Вместимость.
- Количество свободных мест хранения.
- Текущую загруженность.
- Остатки товаров.
- Стоимость хранения и обработки.

Дополнительные требования:

- Подсвечивать выбранный маршрут.
- Визуально различать Mesh и классическую доставку.
- Предусмотреть масштабирование и перемещение по схеме.
- Использовать автоматическое расположение узлов.
- Избегать пересечения стрелок и наложения элементов.
- Отображать недоступные узлы и проблемные сегменты.
- Показывать причины выбора или отклонения маршрута.

#### 5.4. Критерии отбора ПВЗ

Использовать согласованные критерии нашей бизнес-модели:

- Наличие свободных мест хранения.
- Рейтинг ПВЗ не ниже 4,5.
- Допустимая загруженность сотрудников.
- Габариты товара не более 60 × 40 × 40 см.
- Вес товара не более 20 кг.
- Спрос на товар.
- Экономическая выгодность хранения.

Отображать причины допуска или исключения ПВЗ
из маршрута.

Данные ограничения являются условиями предложенной
командой модели, а не официальными правилами RWB.

#### 5.5. Экономическая модель

Для каждого варианта доставки отображать:

- Стоимость перевозки по каждому сегменту.
- Стоимость хранения.
- Стоимость обработки товара.
- Затраты на локальную доставку.
- Затраты на хабы и магистральные перевозки.
- Общие логистические затраты.
- Итоговый срок доставки.

Отдельно отображать показатели участников:

ПВЗ:

- Доходы.
- Расходы.
- Вознаграждения.
- Итоговая прибыль.

Маркетплейс:

- Доходы.
- Расходы.
- Итоговый финансовый результат.

Продавец:

- Начисления.
- Расходы.
- Стоимость хранения.
- Итоговая прибыль.

Покупатель:

- Стоимость доставки.
- Ожидаемый срок доставки.

#### 5.6. Сравнение моделей

Отображать классическую и Mesh-доставку
для одного и того же заказа.

Показывать:

- Разницу логистических затрат в рублях и процентах.
- Разницу стоимости доставки для покупателя.
- Разницу времени доставки в часах и процентах.
- Изменение прибыли участников.
- Преимущества и недостатки каждого маршрута.
- Обоснование выбранного варианта доставки.

Визуально выделять экономию и дополнительные затраты.

Не учитывать внутренние переводы между участниками
как дополнительную прибыль всей логистической цепочки.

Отображать исходные параметры, единицы измерения,
формулы, источники данных и допущения модели.

Не считать Mesh заведомо более выгодным вариантом.
Выбор должен быть обоснован результатами расчётов.

#### 5.7. Демонстрационные сценарии

Использовать Йошкар-Олу и Казань для демонстрации
городских и межгородских заказов.

Предусмотреть визуализацию следующих сценариев:

1. Городской заказ через Mesh без хаба.
2. Межгородской заказ с хабом и магистралью.
3. Возврат заказа и обратная логистика.
4. Логистическая ошибка и перестроение маршрута.
5. Длительное хранение и перерасчёт стоимости.

Отображать влияние изменения загрузки ПВЗ,
длительности хранения, возвратов и логистических
ошибок на стоимость, сроки и прибыль участников.

#### 5.8. Интеграция с backend

- Получать данные узлов, маршрутов, стоимости
  и экономических расчётов через REST API.
- Соблюдать документацию из `docs/openapi`.
- Использовать RTK Query.
- React Flow использовать исключительно
  для визуализации логистической сети.
- Расчёт маршрутов и экономической модели
  выполняется на backend.
- Обновлять визуализацию при изменении данных.
- Обрабатывать состояния загрузки и ошибки API.
- Не изменять backend.
- Не придумывать endpoints и контракты API.
- При отсутствии необходимых данных сообщить мне.
- Не придумывать фактические тарифы и данные RWB.
- Демонстрационные данные и имитируемые операции
  явно обозначать.

Не использовать статические изображения вместо
работающей интерактивной модели.

#### 5.10. Архитектура модели данных

Не привязывать визуализацию к фиксированному
количеству ПВЗ, хабов, городов или маршрутов.

Модель должна динамически строиться на основе
данных, полученных через REST API.

Предусмотреть работу со следующими сущностями:

- Город.
- Логистический узел.
- ПВЗ.
- Хаб.
- Продавец.
- Товар.
- Партия товара.
- Остатки.
- Заказ.
- Маршрут.
- Сегмент маршрута.
- Тариф.
- Экономические показатели.
- Логистический инцидент.

Фактические структуры сущностей и их связи
определяются OpenAPI-документацией.

Использовать уникальные идентификаторы сущностей.

Отделить API-модели от моделей визуализации.

Создать переиспользуемые функции преобразования
данных backend в nodes и edges для React Flow.

Не хранить независимые копии серверных данных
в нескольких компонентах.

Добавление новых ПВЗ, хабов и маршрутов
не должно требовать изменения компонентов.

#### 5.11. Редактирование параметров модели

Предусмотреть изменение параметров моделирования:

- Город отправления и получения.
- Товар и количество.
- Место хранения.
- ПВЗ получения.
- Вместимость и загруженность ПВЗ.
- Длительность хранения.
- Тарифы хранения и перевозки.
- Доступность логистических узлов.

Изменение параметров должно инициировать
повторный расчёт через backend.

Редактирование тестовых параметров отделить
от изменения постоянных данных в базе.

Использовать только предусмотренные API операции.

Если необходимые операции отсутствуют,
согласовать их с backend-разработчиком.

#### 5.12. Визуализация движения заказа

Отображать актуальное состояние заказа
на логистической схеме.

Предусмотреть отображение:

- Текущего логистического узла.
- Пройденных сегментов маршрута.
- Текущего сегмента перевозки.
- Оставшихся сегментов.
- Статуса заказа.
- Ожидаемого времени прибытия.
- Логистических ошибок.
- Обратного маршрута при возврате.

Обновлять модель после изменения статусов.

Использовать обновление кеша RTK Query
после операций и периодический опрос API,
если требуется автоматическое обновление.

Не имитировать реальное GPS-отслеживание,
если backend не предоставляет координаты.

Анимация должна отражать состояние заказа,
а не подменять фактические данные backend.

#### 5.13. Устойчивость экономической модели

Отображать границы приемлемого изменения
стоимости и срока доставки для покупателя.

Проверять следующие условия:

- Положительный результат ПВЗ.
- Безубыточность маркетплейса.
- Экономический результат продавца.
- Приемлемая стоимость доставки для покупателя.
- Приемлемый срок доставки для покупателя.

Предусмотреть отображение влияния:

- Низкой загрузки.
- Перегрузки ПВЗ.
- Длительного хранения.
- Возвратов.
- Логистических ошибок.
- Бонусов и штрафов.
- Нарушений SLA.

Пороговые значения и правила расчёта
согласовывать с backend-разработчиком.

#### 5.14. Масштабирование и поддержка

Использовать переиспользуемые компоненты
узлов, рёбер, таблиц и аналитических карточек.

Не привязывать бизнес-логику к конкретным
городам и тестовым заказам.

Предусмотреть возможность дальнейшего
подключения новых городов, ПВЗ и маршрутов.

Описать ограничения текущего MVP
и направления дальнейшего масштабирования.

## 8. Обязательные сценарии MVP

2.  Межгородской заказ через хаб и магистраль.
3.  Возврат выданного заказа.

## 9. Границы реализации

Отдельное приложение покупателя, реальный платёжный шлюз, системы управления хабами и магистральной логистикой не требуются. Их взаимодействия можно имитировать, явно обозначая заглушки. Используй синтетические данные. Демонстрационный переключатель ролей --- решение команды, а не замена серверной авторизации при работе с реальными данными.
