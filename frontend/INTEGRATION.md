# Проверка интеграции фронтенда

Пять сценариев проверены в Edge с локальным HTTP-стендом, который возвращал синтетические данные по `docs/openapi/frontend.yaml`. Город и межгород прошли через прокси Vite. Возврат, инцидент и длительное хранение проверены на сборке `dist` с активным демопрогоном. Расчёты, остатки и расписание задавал тестовый сервер. Для проверки серверных расчётов и транзакций нужен работающий gateway.

## Подготовка к повторной проверке

Задайте адрес gateway в `MESH_API_PROXY_TARGET`, оставьте `VITE_API_BASE_URL=/api/v1` и запустите `npm run dev` из `frontend`. Для проверки хаба и длительного хранения включите `VITE_API_DEMO_MODE=true`, затем откройте подготовленный демонабор из «Модели доставки». Для отчётов выберите период, который включает модельные даты проводок по UTC.

Ниже приведены исходные условия и ожидаемые переходы. Денежные значения относятся к синтетическому тарифу. При повторном прогоне сверьте суммы из интерфейса с ответами API и привязкой проводок к исходным событиям.

## 1. Городской заказ через Mesh

- **Данные.** `sku-a`, одна единица занимает одно место. ПВЗ хранения `pvz-store`, ПВЗ назначения `pvz-yol`, один физический городской рейс. Исходно в партии 0 единиц, в журнале заказа нет проводок.
- **Шаги.** В `/pvz` примите партию из четырёх единиц. В `/delivery-model` рассчитайте доставку одной единицы и создайте заказ `ord-mesh` по варианту Mesh. В ПВЗ хранения подтвердите сборку и передачу. В ПВЗ назначения подтвердите прибытие и выдачу. В `/analytics` откройте отчёт ПВЗ назначения.
- **Результат.** Заказ прошёл `reserved → packing → in_transit → ready → issued`. После приёмки доступно 4 единицы. После резерва доступно 3 и в резерве 1. После сборки 1 единица собрана. После передачи в исходной партии занято 3 места. До выдачи журнал пуст, после неё расчёт имеет статус `posted`. В отчёте показано вознаграждение ПВЗ 35 ₽. В ответе тестового стенда для продавца проведена продажа на 590 ₽, для маркетплейса расход на логистику 20 ₽.

## 2. Межгород через хаб и магистраль

- **Данные.** Тот же `sku-a`, в исходной партии осталось 3 единицы. ПВЗ назначения `pvz-kzn`. Маршрут из `pvz-store` через два хаба с симулируемой магистралью и физическим последним этапом. Котировка показывает, что прямой вариант Mesh недоступен.
- **Шаги.** Создайте заказ `ord-intercity` по варианту через хаб. Подтвердите сборку и передачу в `pvz-store`. Переведите модельные часы через магистраль до начала последнего этапа. В `pvz-kzn` подтвердите прибытие и выдачу. В `/analytics` откройте отчёт `pvz-kzn`.
- **Результат.** Заказ прошёл `reserved → packing → in_transit → ready → issued`. На этапе `in_transit` после перевода часов последним подтверждённым узлом стал `hub-kzn`. Доступный остаток снизился с 3 до 2. После выдачи `posted`, 35 ₽ вознаграждения ПВЗ, 590 ₽ продажи у продавца и 80 ₽ логистического расхода маркетплейса по данным стенда. Для создания заказа пройден опрос по абсолютному `Location`, для городского заказа — по пути от корня `/api/v1/operations/…`.

## 3. Возврат выданного заказа

- **Данные.** `ord-return` уже выдан, в отчёте начислено продавцу 500 ₽. По возвращаемой единице ещё нет доступного остатка в месте осмотра.
- **Шаги.** Откройте заказ в `/delivery-model`, оформите возврат одной единицы, подтвердите сдачу покупателем, передачу и прибытие. На осмотре отметьте единицу годной к продаже. Сверьте наличие партии в месте осмотра, расчёт продавца и ссылку на исходную проводку в журнале, если API вернул сторно.
- **Результат.** Возврат прошёл `awaiting_dropoff → at_return_point → in_transit → awaiting_inspection → closed`, расчёт перешёл в `posted`. Появилась 1 доступная единица. Начисление продавцу снизилось до 485 ₽, в детализации показана корректировка −15 ₽. Ссылка на исходную запись для сторно проверена отдельно на `/analytics` и в PDF.

## 4. Логистическая ошибка и перестроение маршрута

- **Данные.** `ord-incident` в пути по версии маршрута 1. Сбой относится к активному сегменту `mesh-1`. В тестовом ответе доступен альтернативный рейс.
- **Шаги.** Зарегистрируйте сбой, проверьте блокировку сегмента и запросите пересчёт. Сверьте новый сегмент и дельты в модели с ответом API. Сравните исходное обещание покупателю, цену и остатки до и после.
- **Результат.** Инцидент сменил `blocked` на `resolved`, маршрут сменил версию с 1 на 2. Стоимость исполнения увеличилась на 15 ₽, срок на 1 час. Цена заказа и исходное обещание покупателю сохранились, остатки при пересчёте совпали. Для случая без альтернативного маршрута сверяйте статус `blocked` и причину из API.

## 5. Длительное хранение и перерасчёт

- **Данные.** Две партии `batch-case-keep` и `batch-case-transfer`, порог 60 суток. До перевода часов в выбранном ПВЗ занято 3 места хранения, в тестовом наборе проведено 154 ₽. Партия для вывоза занимает 2 места.
- **Шаги.** В `/delivery-model` переведите модельные часы до случая хранения и проверьте начисление и уведомление. Для первой партии выберите сохранение на ПВЗ и дату повторной проверки. Для второй запланируйте вывоз, подтвердите передачу и прибытие в хаб. Сверьте свободные места в `/pvz`.
- **Результат.** Стенд вернул 93 расчётных слот-суток, начислено 186 ₽, проведено 160 ₽. У первой партии появился статус `deferred`. Вторая прошла `transfer_planned → in_transit → closed`. Два места освободились при передаче. После вывоза в кабинете ПВЗ показано 11 свободных мест из 12.

## Дополнительные проверки

- `npm run build` с генерацией типов OpenAPI и проверкой TypeScript.
- Загрузка и обновление остатков, очереди, версии маршрута, журнала и отчёта после подтверждения операций. Для команд с `202 Accepted` проверены видимое ожидание и опрос до `succeeded`.
- Повтор приёмки и регистрации товара после `503` с прежним `Idempotency-Key`. При `401` интерфейс показывает сообщение о доступе. Демонстрационные роли открывают свои разделы.
- Выгрузка PDF по выбранному периоду и участнику, сравнение двух заказов, длинный журнал, ошибка на второй странице и повтор. Проверены мобильные представления и печатный формат A4.

## Для прогона с gateway

В репозитории в `backend` находится `.gitkeep`. Нужен адрес gateway и данные для пяти сценариев. После подключения проверьте ответы по фактическим ролям и заголовкам `X-Demo-Run-Id` и `Location`, переходы и финансовые результаты. Для запросов с другого origin проверка включает CORS и доступность `Location` из браузера. Интерфейс сейчас использует согласованный демонстрационный переключатель ролей. Если gateway потребует токен для всех запросов, понадобится согласовать способ предоставления доступа к демонстрационным данным.

В публичном контракте отсутствуют заявка продавца на размещение партии, справочник хабов, чтение котировки по ID и прогноз прибыли участников по альтернативным маршрутам. Также в контракте нет параметров котировки для подмены тарифов, загрузки и вместимости. Существующие экраны показывают расчёты из ответов самого API.
