# REST API Mesh Delivery

[Frontend API](frontend.yaml) — контракт единого приложения для ПВЗ, продавца и диспетчера. [Внутренний API](internal.yaml) — контракты вызовов между сервисами. Оба файла самостоятельны, открываются в Swagger Editor и используют OpenAPI 3.0.3.

Для MVP сервисы можно разместить как модули одного backend с PostgreSQL. Пути `/api/v1` обслуживает gateway. Внутренние операции сгруппированы по владельцу. В YAML поля `x-roles`, `x-upstream` и `x-callers` показывают роли, делегирование и разрешенных вызывающих соответственно.

## Сервисы и взаимодействие

| Сервис | Чем владеет | К кому обращается |
| --- | --- | --- |
| `inventory` | SKU, партии, остатки, емкость ПВЗ и интервалы хранения | `routing` за типом узла, `finance` за тарифом и опубликованной стоимостью хранения |
| `routing` | Сеть, рейсы, котировки и резервы мест в рейсах | `inventory` за источниками товара и емкостью ПВЗ, `finance` за тарифами |
| `orders` | Версии заказов и маршрутов, сборка, перемещение и выдача | `routing` за маршрутом и местом в рейсе, `inventory` за резервом и движением, `finance` за проводками |
| `exceptions` | Возвраты, инциденты, длительное хранение и уведомления | `orders` за проверкой выдачи и сменой маршрута, `inventory` за остатком и приемкой, `routing` за обратным путем, `finance` за расчетами |
| `finance` | Версии тарифов, расчетный журнал и аналитика | `orders` за статусом и составом заказа для аналитики продавца |
| `demo` | Готовые наборы, прогоны и модельные часы | `orders` и `exceptions` за плановыми симулируемыми действиями и проверками хранения |

Gateway получает доступ пользователя из токена. `GET /me` позволяет интерфейсу выбрать представление и показать доступные ПВЗ и профили продавца. Сервисы получают подписанную область доступа от gateway. Внутренние вызовы дополнительно авторизуются идентичностью сервиса.

## Функции MVP

Пути в таблице начинаются с `/api/v1`.

| Функция | Основные операции интерфейса | Результат |
| --- | --- | --- |
| А. Приемка и хранение | `POST /products`, `POST /batches`, `GET /batches`, `GET /batches/{batchId}/storage-cost` | Приемка всей партии в пределах квоты и физической емкости. Видны остаток, тариф и стоимость хранения. |
| Б. Оформление и сборка | `POST /quotes`, `POST /orders`, `POST /orders/{orderId}/events` с `packed` | Котировка фиксирует вариант доставки. Заказ резервирует всю корзину. Сборка переводит резерв в упакованное состояние. |
| В. Маршрутизация | `POST /quotes`, `GET /orders/{orderId}/route` | Локальный mesh и путь через хаб сравниваются по сегментам, цене и ETA. Видны причины выбора, ограничения ПВЗ и рейсов. Смешанный маршрут поддерживает несколько источников. |
| Г. Выдача и расчеты | `POST /orders/{orderId}/events` с `issued`, `GET /ledger-entries` | Выдача закрывает заказ и фиксирует вознаграждение ПВЗ, начисления продавцу, удержания и расходы. |
| Д. Нештатные ситуации | `POST /returns`, `POST /incidents`, `POST /incidents/{incidentId}/reroutes`, `GET /storage-cases`, `POST /storage-cases/{caseId}/decisions` | Частичный возврат меняет остатки и проводки. Сбой блокирует сегмент и запускает пересчет. Долго лежащая партия получает начисление, уведомление и решение о дальнейшем хранении или вывозе. |
| Е. Интерфейсы и аналитика | `GET /pickup-points/{pointId}/economics`, `GET /sellers/{sellerId}/economics`, `GET /sellers/{sellerId}/orders/{orderId}/economics` | ПВЗ видит вознаграждение, расходы, удержания и прибыль. Продавец видит начисления и прибыль за период и по отдельному заказу. |

## Сквозные сценарии

1. **Город и межгород.** После приемки запросите котировку для корзины и выбранного ПВЗ. Создайте заказ по варианту и дождитесь резерва. Сборка с местной полки сразу делает отправление готовым. При перевозке идут `packed → handed_over → arrived` по отправлениям и сегментам. Заказ готов после прибытия всех строк. Выдача проводится в выбранном ПВЗ. Хаб и магистраль отмечены `mode: simulated` там, где этапы исполняет симулятор.
2. **Возврат.** Создайте возврат по выданным строкам и количеству. Подтвердите сдачу, движение по обратному маршруту и осмотр. Годный товар пополняет доступный остаток, поврежденный попадает в карантин. Журнал сторнирует начисления в пределах возвращенного количества.
3. **Инцидент.** Зафиксируйте ошибку по отправлению. Диспетчер запрашивает пересчет от последнего подтвержденного узла. Сохраняются пройденные участки, новая версия маршрута, изменение цены исполнения и ETA. Если пути пока нет, интерфейс показывает `blocked` и причину. Исходное обещание и цена покупателя сохраняются для сравнения.
4. **Долгое хранение.** Сервис проверяет порог и обновляет начисления. Диспетчер выбирает `keep` с датой повторной проверки или `transfer_to_hub` с обоснованием. Уведомления отображаются через `GET /notifications`. При вывозе слоты ПВЗ освобождаются по фактической передаче.
5. **Демонстрация.** `GET /demo/datasets` показывает готовые наборы. `POST /demo/runs` создает и активирует чистый прогон. Интерфейс берет актуальный ID из `GET /demo/context` и передает его в `X-Demo-Run-Id`. `POST /demo/clock/advances` доводит плановые симулируемые этапы и начисления до заданного времени. Переключение работает с подготовленными наборами и изолирует предыдущий прогон.

## Правила обработки

- **Повтор.** Для команд с `Idempotency-Key` повторите исходный запрос с прежним ключом. Версии заказа, возврата и случая хранения защищают от параллельного изменения. Транзакции склада отдельно проверяют доступные количества и слоты, включая конкуренцию за последнюю единицу.
- **Подтверждение.** На `202 Accepted` используйте `Location` и ждите `succeeded` или `failed`. У первой команды создания заказа ID заказа появляется в `resourceId` после закрепления резервов. Выдача считается обработанной после учета товара и расчета начислений. Промежуточное `settlementStatus: pending` показывает, что расчет еще идет.
- **Списание.** Сборка меняет состояние резерва. Первая физическая передача уводит единицу из исходной партии. В ПВЗ назначения выдача снимает ее с учета выдачи. Для заказа с местной полки физическое выбытие происходит при выдаче. В СЦ учитывается транзит, длительное хранение закрепляется за партией.
- **Частичные сбои.** При отказе до подтверждения заказа владелец процесса освобождает предварительные резервы. После физического события сервис повторяет незавершенные шаги по устойчивым ключам. Каждая проводка привязана к исходному событию, сторно ссылается на исходную запись.
- **Стоимость.** Суммы в целых копейках. Котировка разделяет расчетные затраты сети и цену покупателя. Отчеты используют проведенные суммы и период `[from, to)`. Хранение считается по полным 24-часовым периодам с момента приемки единицы, с закрепленной ставкой за слот-сутки.

## Локальный веб-просмотр

Из корня репозитория запустите `python3 docs/openapi/view.py --port 8080` и откройте [localhost:8080](http://127.0.0.1:8080). Swagger UI загружается с CDN unpkg.com и показывает оба контракта с поиском по операциям. Чтобы открыть контракты без локального сервера, выполните `python3 docs/openapi/view.py --export mesh-openapi.html` и откройте полученный HTML в браузере.
